# S02 — Identity & Key Protection

## Overview

Each Najwa profile holds exactly one identity: an Ed25519 key pair created on
the computer. Contacts learn the public key when they accept an invitation. It
anchors what they verify later: the invitation signature, the mailbox
certificates and the X3DH handshake.

The identity private key is stored encrypted in a 192-byte identity record in
the profile directory. Opening the record needs two independent factors:

- the **passphrase**, stretched with Argon2id; and
- the **device factor** (DKM), 32 random bytes kept outside the record. A TPM 2.0
  key protects it on Windows and Linux; a Secure Enclave key wraps it on macOS. If
  hardware protection fails, the user may approve the operating system's key
  storage for that identity. The app never falls back to OS storage silently.

Neither factor alone opens the record. A copied profile directory is useless
without the device factor, and the device factor is useless without the
passphrase.

Unlocking goes through a persistent, authenticated attempt counter: exponential
backoff after each wrong passphrase and a lockout after ten. Every attempt runs
the full Argon2id derivation and is padded to a minimum duration, so timing does
not reveal which check failed.

A **recovery kit** handles a forgotten passphrase or a lost device factor. It has
two parts: 24 words and a 105-byte encrypted recovery file. The words encode an
independent random recovery seed. The file holds a copy of the identity private
key encrypted under a key derived from that seed. Both parts are needed.
Recovery restores the identity key and installs a new record under a new
passphrase and a new device factor. In the original profile, contacts and
conversations stay readable because the database key derives from the identity
key. In an empty profile, recovery restores the identity only. After any
recovery the messaging layer publishes fresh prekeys before it accepts new
sessions.

Mailboxes never see the identity key. Each mailbox sees a signing key derived
from it for that mailbox only (§2.2).

The native local service (`apps/local-web`) owns the identity manager specified
here. After unlock it hands the identity to the messaging client, which opens
the SQLCipher store ([S03](03-encrypted-storage.md)), signs invitations and
mailbox certificates ([S05](05-contact-establishment.md)) and runs X3DH
([S06](06-key-agreement-ratchet.md)). Locking and profile erasure are specified
in [S13](13-privacy-hardening.md).

## 2. Identity Key

- **Algorithm:** Ed25519 ([RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032)).
- **`IK_priv`:** the 32-byte Ed25519 private key (the RFC 8032 secret seed),
  generated by the OS CSPRNG.
- **`IK_pub`:** the 32-byte Ed25519 public key.

```
IK_priv = CSPRNG(32)
IK_pub  = Ed25519_PublicKey(IK_priv)
```

The identity key:

- signs the invitation (handshake payload) — [S05 §2](05-contact-establishment.md);
- signs one `MailboxCertificate` per mailbox — [S05 §2.3](05-contact-establishment.md);
- is the input key material of the per-mailbox signing keys (§2.2);
- converts to X25519 for X3DH ([S06 §2](06-key-agreement-ratchet.md)) and for
  pairwise pseudonyms ([S05](05-contact-establishment.md));
- derives the database key (§4.2).

`IK_priv` is persisted only in encrypted form: in the identity record (§7.1) and
in the recovery record (§13.0). An implementation MUST NOT persist it in any
other form.

### 2.1 Identity Key Transmission

`IK_pub` is sent only to contacts:

1. In the invitation (handshake payload), signed by `IK_priv`, shared as a link
   or QR code ([S05 §2](05-contact-establishment.md)).
2. In the `ik_pub` field of each `MailboxCertificate` inside that invitation
   ([S05 §2.3](05-contact-establishment.md)).
3. In the X3DH header of an Initial message ([S06 §2](06-key-agreement-ratchet.md)),
   carried inside the encrypted deposit envelope ([S07 §3](07-message-format.md)).

Prekey bundles uploaded to a mailbox carry that mailbox's derived signing key,
not `IK_pub` (§2.2). `IK_pub` MUST NOT be published in a directory, sent to
unknown parties or used as a network identifier.

### 2.2 Per-Mailbox Signing Keys

For each mailbox, the client derives a separate Ed25519 signing key:

```
seed = HKDF-SHA256(
    IKM    = IK_priv,
    salt   = UTF8(onion_address),
    info   = "najwa/v1/mailbox-signing-key",
    length = 32
)
(mailbox_ik_priv, mailbox_ik_pub) = Ed25519 key pair from seed
```

`onion_address` is the mailbox's 56-character v3 onion address as stored in the
mailbox configuration, without the `.onion` suffix. The derivation is
deterministic, so recovery reproduces the same keys.

The derived key signs the signed prekeys and prekey manifests published to that
mailbox ([S06 §4.2](06-key-agreement-ratchet.md),
[S06 §5.4](06-key-agreement-ratchet.md)). Different mailboxes therefore see
different, unrelated public keys. A contact links a derived key to the identity
through a `MailboxCertificate`:

```
cert_signable = ik_pub(32) || mailbox_ik_pub(32) || mailbox_onion(56) ||
                created_at(8, BE) || expires_at(8, BE)
signature     = Ed25519_Sign(IK_priv, cert_signable)
expires_at    = created_at + 15,552,000          // 180 days
```

The certificate layout and its verification are specified in
[S05 §2.3](05-contact-establishment.md). Derived keys hide the identity from
mailbox operators. They do not prevent correlation through traffic timing,
capability structure or information outside the protocol.

## 3. 2-of-2 Key Protection

Unlocking the identity key REQUIRES both:

1. **Knowledge factor:** the passphrase, processed with Argon2id (§6).
2. **Possession factor:** the device factor `DKM`, held by a hardware backend or,
   after explicit approval, by OS key storage (§17).

Compromise of either factor alone MUST NOT reveal `IK_priv`. The recovery kit
(§13) is a separate path that needs neither factor.

### 3.1 Security Goals

| ID | Goal | Description |
|----|------|-------------|
| G1 | Confidentiality at rest | `IK_priv` MUST NOT be recoverable from the profile without both factors or a complete recovery kit |
| G2 | Two-factor (2-of-2) | The passphrase alone MUST NOT unlock; the device factor alone MUST NOT unlock |
| G3 | Offline attack resistance | A copy of the identity record MUST resist passphrase guessing through Argon2id and the device factor |
| G4 | Device binding | A record copied to another computer MUST NOT unlock there. Hardware backends bind `DKM` to the TPM or Secure Enclave; approved OS storage binds it to the OS account's credential store (§20) |
| G5 | Passphrase change | The user MUST be able to change the passphrase without changing the identity key |
| G6 | Corruption detection | Accidental modification of the record MUST cause unlock failure |

## 4. Standard Mode Key Derivation

### 4.1 Derivation Flow

```
Step 1: Passphrase → Argon2id → K_pwd (32 bytes)
  pw    = UTF8(NFC(passphrase))
  K_pwd = Argon2id(pw, saltP, memory, iterations, parallelism, 32)

Step 2: Combine with the device factor → KEK
  PRK = HKDF-Extract(salt = DKM, IKM = K_pwd)
  KEK = HKDF-Expand(PRK, info = "najwa/v1/kek", length = 32)

Step 3: Decrypt the identity key
  IK_priv = XChaCha20-Poly1305-Decrypt(KEK, nonce, enc_ik, AAD_identity)

Step 4: Verify
  Ed25519_PublicKey(IK_priv) == ik_pub        (constant-time comparison)
```

`DKM` as the HKDF salt enforces the device factor: without the device's `DKM`
the correct `KEK` cannot be derived, even with the correct passphrase.

**Creating a record.** Identity creation (§18) and recovery (§13.2) build a new
record as follows:

```
 1. pw = UTF8(NFC(passphrase)); FAIL if passphrase is empty
 2. IK_priv = CSPRNG(32)                  (recovery: the recovered key)
 3. DKM = CSPRNG(32)
 4. (memory, iterations, parallelism) = calibrate (§6.3)
 5. saltP = CSPRNG(32)
 6. K_pwd = Argon2id(pw, saltP, params, 32); zeroize pw
 7. KEK = HKDF-Expand(HKDF-Extract(DKM, K_pwd), "najwa/v1/kek", 32); zeroize K_pwd, PRK
 8. nonce = CSPRNG(24)
 9. Fill the header fields of §7.1 (version 0x03, mode 0x01, reserved 0x000000)
10. enc_ik = XChaCha20-Poly1305-Encrypt(KEK, nonce, IK_priv, AAD_identity)   // 48 bytes
11. checksum = SHA-256(record[0:160])
12. Store DKM as this record's generation (§17); zeroize KEK and DKM copies
```

The record is not yet on disk after step 12. It becomes live through the
generation commit (§12.3).

### 4.2 Database Key Derivation

The SQLCipher key derives from the identity key alone:

```
db_key = HKDF-SHA256(
    IKM    = IK_priv,
    salt   = "najwa-sqlcipher-key",
    info   = "najwa/v1/sqlcipher-key",
    length = 32
)
```

A passphrase change or a recovery keeps `IK_priv` and therefore keeps `db_key`.
See [S03 §3](03-encrypted-storage.md) for how `db_key` opens the store.

## 6. Argon2id Parameters

### 6.1 Constraints

Normative bounds. See [S01 §3.8](01-crypto-primitives.md) for the primitive.

```
ARGON2_VERSION         = 0x13             // v1.3
ARGON2_TYPE            = Argon2id
ARGON2_MIN_MEMORY_KIB  = 65536            // 64 MiB, hard floor
ARGON2_MAX_MEMORY_KIB  = 4194304          // 4 GiB
ARGON2_MIN_ITERATIONS  = 3
ARGON2_MAX_ITERATIONS  = 100
ARGON2_MIN_PARALLELISM = 1
ARGON2_MAX_PARALLELISM = 16
ARGON2_TAG_LENGTH      = 32
```

A derivation with parameters outside these bounds MUST fail.

### 6.2 Platform Targets

| Parameter | Floor | Desktop target | Maximum |
|-----------|-------|----------------|---------|
| Memory (KiB) | 65,536 (64 MiB) | 524,288 (512 MiB) | 4,194,304 (4 GiB) |
| Iterations | 3 | Smallest count ≥ 3 whose trial takes ≥ 1000 ms | 100 |
| Parallelism | 1 | Available CPU cores | 16 |

**Calibration target:** at least 1000 ms on the computer that creates the record.
Calibration only increases iterations. It never drops below 3 iterations to meet
the target, so a slow computer can take longer than 1000 ms. A slower derivation
raises an attacker's guessing cost; a faster one would weaken the passphrase
factor.

### 6.3 Calibration Procedure

```
1. memory      = 524288 KiB
2. parallelism = clamp(available CPU cores, 1, 16)
3. Run one Argon2id hash at (memory, 3, parallelism).
   If its working memory cannot be allocated:
     if memory > 65536: memory = max(memory / 2, 65536); go to 3
     else: FAIL — the identity cannot be created
4. iterations = 3
5. Loop:
     elapsed = duration of one Argon2id hash at (memory, iterations, parallelism)
     if elapsed >= 1000 ms or iterations >= 100: return (memory, iterations, parallelism)
     iterations = iterations + 1
```

The calibrated parameters are stored in the record (§7.1) and used for the life
of that record. Unlock and passphrase change reuse them. Recovery calibrates
again because it creates a new record. A computer that cannot allocate 64 MiB
for Argon2id cannot create an identity.

## 7. Identity Record Format

### 7.1 Standard Mode (192 bytes, fixed)

Stored in the profile as `identity.najwa`. Multi-byte integers are big-endian.

| Offset | Size | Field | Description |
|--------|------|-------|-------------|
| 0 | 8 | `magic` | `NAJWA\x00\x00\x00` (hex `4E414A5741000000`) |
| 8 | 1 | `version` | `0x03` |
| 9 | 1 | `mode` | `0x01` (Standard) |
| 10 | 1 | `kdf_alg` | `0x01` (Argon2id) |
| 11 | 1 | `aead_alg` | `0x01` (XChaCha20-Poly1305) |
| 12 | 4 | `argon2_memory` | Memory in KiB |
| 16 | 4 | `argon2_iterations` | Time cost |
| 20 | 1 | `argon2_parallelism` | Lanes |
| 21 | 3 | `reserved` | MUST be `0x000000` |
| 24 | 32 | `saltP` | Passphrase salt (CSPRNG); also names the device-factor generation (§17.1) |
| 56 | 24 | `nonce` | AEAD nonce (CSPRNG) |
| 80 | 32 | `ik_pub` | Identity public key (Ed25519) |
| 112 | 48 | `enc_ik` | Encrypted `IK_priv` (32 bytes) + Poly1305 tag (16 bytes) |
| 160 | 32 | `checksum` | SHA-256 of bytes 0–159 |

Total: 192 bytes.

```
MAGIC              = "NAJWA\x00\x00\x00"
VERSION            = 0x03
MODE_STANDARD      = 0x01
MODE_HARDWARE      = 0x02     // reserved; never written (§19.3)
KDF_ALG_ARGON2ID   = 0x01
AEAD_ALG_XCHACHA20 = 0x01
```

Writers MUST write version `0x03`, mode `0x01`, `kdf_alg` `0x01`, `aead_alg`
`0x01` and a zero `reserved` field. Readers MUST reject a file shorter than 192
bytes; bytes after offset 191 are ignored. Readers MUST treat as invalid a record
with a wrong `magic`, a `version` greater than `0x03`, a nonzero `reserved` field
or a checksum mismatch. During unlock these checks are recorded without an early
return (§9.1). `mode`, `kdf_alg` and `aead_alg` are bound into the AEAD (§8.1), so
a record with any other value in these bytes cannot unlock.

### 7.3 Checksum

The checksum detects corruption only. It is not a tamper defense:

- It detects bit flips, truncation and storage errors.
- `checksum = SHA-256(record[0:160])`, over every preceding byte including `reserved`.
- An attacker with write access can recompute it.
- Tampering is caught by the AEAD: a changed authenticated field makes decryption fail.

`reserved` is covered by the checksum and verified on parse, but it is not part
of the AAD.

### 7.5 Profile Files

All identity files live in the profile directory and are written with the atomic
write of §12.2. `<gen>` is the record's generation id (§17.1).

| File | Size | Content | Written | Removed |
|------|------|---------|---------|---------|
| `identity.najwa` | 192 B | Identity record (§7.1) | Generation commit (§12.3) | Profile erasure |
| `identity.recovery` | 105 B | Recovery record (§13.0) | Identity creation, kit replacement (§13.5), restore into an empty profile (§13.2) | Profile erasure |
| `identity.counter.<gen>` | 44 B | Attempt counter (§10.1) | Every unlock attempt; generation commit | After the next generation commits |
| `identity.timing.<gen>` | 40 B | Unlock timing reference (§9.1) | Generation commit; each successful unlock | After the next generation commits |
| `prekey-recovery-<hex(ik_pub)>` | 32 B | Prekey-recovery generation (§13.2) | Before a recovered record is installed | Kept; the store records completion |
| `identity.tmp.<16 hex>` | — | Temporary file of an atomic write | During §12.2 | Renamed over the target, or deleted on failure |

The device factor itself is never in the profile directory (§17).

## 9. Unlock Procedure

Every unlock attempt MUST take approximately the same time regardless of which
check fails, so that timing gives no oracle.

### 9.1 Steps (Standard Mode)

The procedure runs inside the attempt limiter (§10.1), which has already counted
the attempt. `T_ref` is the timing reference described below.

```
 1. Take the loaded record. start = monotonic_now(); failed = false
 2. Validate structure (§7.1): magic, version <= 0x03, reserved == 0.
    On failure: failed = true. DO NOT return early.
 3. Compare SHA-256(record[0:160]) with checksum in constant time.
    On mismatch: failed = true. DO NOT return early.
 4. DKM = the device factor of this record's generation (§17.2).
    If unavailable: DKM = CSPRNG(32); failed = true. DO NOT return early.
 5. Take the passphrase.
 6. pw = UTF8(NFC(passphrase)). If the passphrase is empty: pw = fixed dummy bytes;
    failed = true.
 7. ALWAYS run Argon2id with the record's parameters, even after earlier failures:
      t0 = monotonic_now()
      K_pwd = Argon2id(pw, saltP, params, 32)
      T_argon = monotonic_now() - t0
    If Argon2id fails (parameters out of bounds, allocation failure):
      K_pwd = 0^32; failed = true.
    Zeroize pw.
 8. PRK = HKDF-Extract(salt = DKM, IKM = K_pwd)
    KEK = HKDF-Expand(PRK, "najwa/v1/kek", 32)
    Zeroize K_pwd, PRK.
 9. AAD = AAD_identity (§8.1)
10. m = XChaCha20-Poly1305-Decrypt(KEK, nonce, enc_ik, AAD)
11. If decryption succeeded, |m| == 32 and not failed:
      derived_pub = Ed25519_PublicKey(m)
      if not constant_time_eq(derived_pub, ik_pub): failed = true
    else:
      failed = true
12. Enforce the minimum duration:
      minimum = T_ref + T_ref / 10 + 200 ms
      elapsed = monotonic_now() - start
      if elapsed < minimum: sleep(minimum - elapsed + uniform(0, 50) ms)
13. success = not failed (structure, checksum, device factor, KDF, decryption
    and public-key checks all passed).
14. If not success: zeroize all intermediates; return the single generic error
    UnlockFailed. DO NOT indicate which check failed.
15. If success: zeroize KEK and DKM; return the identity and T_argon.
```

**Timing reference.** `T_ref` is the Argon2id duration of the last successful
unlock of this generation. It is stored in `identity.timing.<gen>`:

```
duration_ns(8, u64 BE) || tag(32)
tag = HMAC-SHA256(key = DKM, "last-successful-argon-time" || duration_ns(8, BE))
```

- A new generation starts with `T_ref = 1000 ms` (the calibration target, §6.2),
  so even the first unlock has no distinguishable timing. A passphrase change
  instead stores the `T_argon` measured while authenticating the current
  passphrase.
- After each successful unlock, `T_ref = T_argon` is written back. A failed
  attempt never changes `T_ref`.
- A missing, wrongly sized or unauthenticated timing file yields `T_ref = 1000 ms`.
  Deleting or forging the file therefore cannot shorten the floor below the
  creation seed.

After a successful unlock, the app passes the identity to the messaging client,
which derives `db_key` (§4.2) and opens the store.

### 9.2 UI Oracle Prevention

- A wrong passphrase, a record that fails validation and a record that fails
  decryption all produce the same error, reported by the app as
  `authentication_failed`.
- The limiter reports `rate_limited` (with `retryAfterMs`) or `locked_out` before
  the passphrase is tested. A device-factor failure before the test is reported
  as `keystore_unavailable`. These depend only on limiter and device state and
  reveal nothing about the passphrase.
- The duration floor of §9.1 step 12 applies to every outcome of the passphrase
  test.

## 10. Rate Limiting

### 10.1 Attempt Counter

Each record generation has a persistent counter `N` and a last-attempt time,
stored in `identity.counter.<gen>`:

| Offset | Size | Field |
|--------|------|-------|
| 0 | 4 | `attempts` (`N`, u32 BE) |
| 4 | 8 | `last_attempt` (Unix seconds, u64 BE; 0 when none) |
| 12 | 32 | `tag = HMAC-SHA256(key = DKM, "attempt-counter" \|\| attempts(4, BE) \|\| last_attempt(8, BE))` |

Total: 44 bytes.

**Loading.** The counter is read when the identity manager loads the record (at
profile open, and again when an unlocked identity is locked) and again at the
start of every attempt (step 0 below). An expired lockout, a counter written by
another process, or a `DKM` that has become readable since the profile opened
(a keyring unlocked later) therefore takes effect without a restart. If the
record was loaded while its `DKM` was unreadable, the attempt first switches to
the files of the record's generation once the `DKM` can be read.

- If the file is exactly 44 bytes and the tag verifies under the generation's
  `DKM`: when `now − last_attempt > 86,400 s`, `N = 0`; otherwise the stored
  values apply.
- Otherwise — file missing, wrong size, unreadable, tag invalid, or `DKM`
  unavailable — `N = UNLOCK_MAX_ATTEMPTS` (fail closed). This state is not
  written back and lasts while the file stays unauthenticated or the `DKM`
  unreadable. The recovery kit (§13.2) installs a new generation with `N = 0`.

**Each attempt.** Unlock, passphrase change (§12.1) and kit replacement (§13.5)
authenticate the passphrase through the same procedure:

```
0. Load N and last_attempt from the counter file (Loading, above).
1. If N >= UNLOCK_MAX_ATTEMPTS: FAIL LockedOut. The passphrase is not tested.
2. If N >= 1 and now − last_attempt < delay(N): FAIL RateLimited(delay(N)).
3. N = N + 1; last_attempt = now; write the counter file (§12.2).
   If the write fails: FAIL. The passphrase is not tested.
4. Run the unlock procedure (§9.1).
5. On failure: last_attempt = now (the delay counts from the end of the KDF);
   write the counter file; FAIL UnlockFailed.
6. On success: N = 0; last_attempt = 0; write the counter file.
```

Counting the attempt durably before the passphrase is tested means a crash or a
killed process cannot hide a guess. A new generation starts with `N = 0`.

### 10.2 Delay Calculation

```
UNLOCK_MAX_ATTEMPTS = 10
delay(N) = 1000 ms × 2^min(N − 1, 10)    for N >= 1
delay(0) = 0
```

| Failed attempts (N) | Wait before the next attempt |
|---------------------|------------------------------|
| 0 | none |
| 1 | 1 s |
| 2 | 2 s |
| 3 | 4 s |
| 4 | 8 s |
| 5 | 16 s |
| 6 | 32 s |
| 7 | 64 s |
| 8 | 128 s |
| 9 | 256 s |
| ≥ 10 | Locked out |

After 10 consecutive failures the identity stays locked out until more than
24 hours have passed since the last failed attempt, or until the recovery kit is
used. The next attempt after the 24 hours is accepted without restarting the
app, because each attempt reloads the counter (§10.1).

## 11. Password Requirements

### 11.1 Minimum

A new passphrase (identity creation, passphrase change, recovery, restore) MUST:

- be at least 12 characters long, counted in Unicode scalar values;
- be at most 1024 bytes as UTF-8;
- be entered twice, with both entries identical;
- have an estimated guessing cost of at least 2^40 (40 bits), by zxcvbn 3.1.1,
  both for the passphrase as entered and with all whitespace removed. Word
  separators are predictable, so an attacker can omit them.

zxcvbn's dictionaries (common passwords, English words, names and surnames, also
reversed and with l33t substitutions) and its repeat, sequence, keyboard-pattern
and date matchers give a common password, a repeated character, a sequence or a
keyboard pattern an estimate far below 2^40, so these are refused. Its password
list holds the 30,000 most common passwords, not 100,000. A common password
outside that list is refused only when its estimate falls below 2^40. zxcvbn
evaluates the first 100 characters. A refusal returns `weak_passphrase` with
zxcvbn's warning, if it has one.

The identity core enforces the length and strength rules, not only the user
interface: `validate_new_passphrase` runs at the start of every identity-manager
function that sets a new passphrase (`create`, `create_with_recovery_record`,
`change_password`, `recover_from_seed`, `recover_from_recovery_record_at`),
before any state changes, so a refused passphrase writes nothing and costs no
unlock attempt. It returns `PasswordTooShort`, `PasswordTooLong` or
`WeakPassphrase` (with zxcvbn's warning as the hint). The C ABI reports all
three as `NAJWA_WEAK_PASSPHRASE` ([S17 §2](17-ffi-bindings.md)). Confirmation
stays with the caller that collects the passphrase twice.

A passphrase entered to unlock MUST be non-empty and at most 1024 bytes. The
strength rule never applies to unlock, so an identity created under an earlier,
weaker rule still opens.

### 11.2 Recommended

- Estimated entropy ≥ 50 bits.
- Passphrase of 4 or more words from a 7,776-word list (≥ 51.7 bits), or 5 or
  more words from a 2,048-word list (≥ 55 bits).

### 11.3 Normalization

The passphrase is normalized to Unicode NFC and encoded as UTF-8 before Argon2id:
`pw = UTF8(NFC(passphrase))`. Two inputs that differ only in Unicode composition
therefore unlock the same record. Length limits apply to the input as entered.

## 12. Password Change

### 12.1 Procedure

The app locks the messaging client before the change and attaches the identity
again after it succeeds.

```
 1. R = the current record (re-read from disk if the identity is unlocked).
 2. Authenticate the current passphrase against R through the limiter (§10.1).
    This counts as an unlock attempt. Failure aborts.
 3. Validate the new passphrase (§11.1); pw' = UTF8(NFC(new_passphrase)).
 4. params = R's Argon2id parameters (no recalibration).
 5. saltP' = CSPRNG(32)
 6. K_pwd' = Argon2id(pw', saltP', params, 32)
 7. DKM = the device factor of R's generation (§17.2)
 8. KEK' = HKDF-Expand(HKDF-Extract(DKM, K_pwd'), "najwa/v1/kek", 32)
 9. nonce' = CSPRNG(24)
10. R' = R with saltP', nonce', mode 0x01, kdf_alg 0x01, aead_alg 0x01
    enc_ik' = XChaCha20-Poly1305-Encrypt(KEK', nonce', IK_priv, AAD_identity(R'))
    checksum' = SHA-256(R'[0:160])
11. Store DKM as the new generation hex(saltP') (§17). The same DKM value is
    re-protected under a new credential and, on hardware backends, a new hardware key.
12. Commit R' (§12.3) with T_ref = the T_argon measured in step 2.
13. Zeroize all intermediates.
```

The identity key does not change, so contacts, sessions and the database are
unaffected.

### 12.2 Atomic Write

Every identity file is replaced atomically:

```
1. temp = the target path with its extension replaced by
   "tmp." || 16 lowercase hex digits of 8 CSPRNG bytes
   (example: identity.najwa → identity.tmp.3f09c1e2a4b5d677)
2. Create temp, write the data, fsync(temp).
3. Replace the target with temp durably (below), replacing an existing target.
On a failure in step 2 or 3: delete temp and report the error.
```

The random temporary name prevents a pre-created file or symlink at a
predictable path, and collisions between concurrent writers.

The replacement MUST be durable before the write reports success, so that a
caller may then destroy what the previous file needed (§12.3 step 5):

- **POSIX (Linux, macOS):** `rename(2)`, then `fsync` of the parent directory. A
  failure to open or sync the directory is reported, except `EINVAL` (the file
  system cannot sync a directory).
- **Windows:** `MoveFileExW(temp, target, MOVEFILE_REPLACE_EXISTING |
  MOVEFILE_WRITE_THROUGH)`. A plain rename is atomic but not durable on Windows.

A reported failure in step 3 can come after the new file became visible, with
its durability unconfirmed. The caller must then treat both versions as possible.

Crash behavior:

- Crash before the rename: the previous file is intact; a stale temporary file
  may remain.
- Crash after the write reported success: the new file is in place.

### 12.3 Generation Commit

Creation (§4.1), passphrase change (§12.1) and recovery (§13.2) install a new
record `R'` whose `DKM` is already stored under generation `gen'` (§17.1). The
rename of `identity.najwa` is the commit point:

```
1. Write identity.counter.<gen'> with N = 0, and identity.timing.<gen'> with T_ref.
2. If a recovery record RR comes with R' (identity creation):
     keep a copy of the current identity.recovery, if any;
     write RR to identity.recovery (§12.2).
3. Write R' to identity.najwa (§12.2).                      — commit point
4. If step 1, 2 or 3 fails:
     restore the previous identity.recovery (or delete it if there was none);
     unless identity.najwa now holds R' (step 3 failed after the replace):
       delete gen' (§17.6) and its counter and timing files;
     report the error. The previous record and its generation are untouched.
5. After the commit (step 3 reported success, so R' is durable): delete the
   previous generation's credential, counter and timing files. A credential
   deletion failure is logged and does not undo the commit.
```

When step 3 fails after R' became visible, both generations are kept: until R'
is known to be durable, a power cut may leave either record, and each still has
its `DKM`. The previous generation may then remain as an unused credential.

An interruption before step 3 leaves the previous identity usable. An
interruption after step 3 leaves everything the new record needs in place; the
previous generation may remain as an unused credential.

## 13. Recovery Kit (BIP-39 Words and Recovery File)

The recovery kit is two parts that are useless apart:

1. **Recovery words:** a BIP-39 mnemonic (English word list) encoding a random
   `recovery_seed`. The app generates 24 words.
2. **Recovery file:** the 105-byte recovery record (§13.0), holding `IK_priv`
   encrypted under a key derived from `recovery_seed`.

> **Two separate secrets.**
>
> | | Identity key `IK_priv` (§2) | Recovery seed (this section) |
> |---|---|---|
> | Size | 32 bytes | 32 bytes (24 words) or 16 bytes (12 words) |
> | Generated | Once, at identity creation | Each time a recovery record is created |
> | Persisted | Only encrypted, in the identity and recovery records | Never; only the words the user writes down |
> | Role | Signing and key agreement | Input to `K_recovery`, which decrypts the stored copy of `IK_priv` |
>
> Recovery decrypts the stored `IK_priv`. It never derives `IK_priv` from the
> words. The words are not a backup of message history.

### 13.0 Recovery Record Storage and Lifecycle

Layout (105 bytes, no padding):

| Offset | Size | Field |
|--------|------|-------|
| 0 | 32 | `ik_pub` — identity public key (HKDF salt and AAD input) |
| 32 | 24 | `nonce_recovery` — AEAD nonce |
| 56 | 48 | `enc_ik_recovery` — `IK_priv` (32 bytes) + Poly1305 tag (16 bytes) |
| 104 | 1 | `phrase_length` — 12 or 24 |

The record has no magic, version or checksum. Its integrity comes from the AEAD:
`ik_pub` is both the HKDF salt and part of the AAD, and the recovered key is
checked against `ik_pub` (§13.2 step 7).

| Property | Identity record (§7) | Recovery record |
|----------|----------------------|-----------------|
| Location | `identity.najwa` | `identity.recovery` in the profile; the exported copy is named `najwa-<first 12 hex digits of ik_pub>.recovery` |
| Encrypted by | `KEK` (passphrase + `DKM`) | `K_recovery` (recovery seed) |
| Needed to unlock | Yes | No |
| Needed to recover | No | Yes, with the words |
| Bound to the device | Yes, through `DKM` | No; usable on any computer |
| Lifetime | Until the next generation commits | Until the kit is replaced (§13.5) or the profile is erased |

**Creation.** `create_with_recovery_record` creates the identity and its
recovery record together. The recovery record is written in the same generation
commit as the identity record (§12.3 step 2) and rolled back if the identity
record cannot be written.

**Handing the kit to the user.** The words are kept only in native memory. While
the identity is unlocked and the kit is pending, the app returns the words
(`recovery_words`) and the record as base64 (`export_recovery`); the UI saves the
record as the raw 105-byte file. `acknowledge_recovery`, a lock or a restart
discards the words.

**Erasure.** Profile erasure ([S13 §11](13-privacy-hardening.md)) MUST remove
both `identity.najwa` and `identity.recovery`. Copies the user exported are
outside the profile and are not erased.

### 13.1 Generation

```
1. phrase_length ∈ {12, 24}; the app uses 24.
2. recovery_seed = CSPRNG(32 if phrase_length = 24, 16 if 12)
   // independent of IK_priv
3. words = BIP39_Encode(recovery_seed)            // English word list
4. K_recovery = HKDF-SHA256(
       IKM    = recovery_seed,
       salt   = ik_pub,
       info   = "najwa/v1/recovery",
       length = 32
   )
5. nonce_recovery = CSPRNG(24)
6. enc_ik_recovery = XChaCha20-Poly1305-Encrypt(
       key = K_recovery, nonce = nonce_recovery,
       plaintext = IK_priv, aad = AAD_recovery     // §8.6
   )
7. RecoveryRecord = ik_pub || nonce_recovery || enc_ik_recovery || phrase_length
8. Zeroize recovery_seed, K_recovery and the IK_priv working copy.
9. Return words (shown once) and RecoveryRecord (persisted).
```

**Why HKDF and not Argon2id:** `recovery_seed` already carries 256 bits (24
words) or 128 bits (12 words) of entropy. Exhaustive search is infeasible at any
KDF cost, so a slow KDF would only delay legitimate recovery.

### 13.2 Recovery

**Algorithm.** Inputs: words `W`, recovery record `RR`, new passphrase `P'`.

```
 1. Count the whitespace-separated words of W.
 2. Every word MUST be in the BIP-39 English word list.
 3. recovery_seed = BIP39_Decode(W)            // checksum verified; else FAIL
 4. Load RR (105 bytes, §13.0). RR.phrase_length MUST be 12 or 24 and MUST equal
    the word count of step 1; else FAIL "phrase length mismatch".
 5. K_recovery = HKDF-SHA256(IKM = recovery_seed, salt = RR.ik_pub,
                             info = "najwa/v1/recovery", length = 32)
 6. IK_priv = XChaCha20-Poly1305-Decrypt(K_recovery, RR.nonce_recovery,
                                         RR.enc_ik_recovery, AAD_recovery(RR.ik_pub))
    On failure: FAIL.
 7. If Ed25519_PublicKey(IK_priv) ≠ RR.ik_pub: FAIL.
 8. Validate P' (§11.1). Build a new record from IK_priv under P' (§4.1): new DKM,
    new saltP, new nonce, freshly calibrated Argon2id parameters.
 9. Write the prekey-recovery marker (below), then commit the new record (§12.3)
    with T_ref = 1000 ms. The counter starts at N = 0.
10. Zeroize recovery_seed, K_recovery and IK_priv working copies.
```

Steps 1–4 may run in any order; all of them complete before any key is
derived. A failure at any step leaves the current profile unchanged. Recovery
never returns a different identity: a wrong phrase fails AEAD authentication at
step 6.
Recovery attempts do not pass through the attempt counter (§10); their strength
is the 128- or 256-bit recovery seed.

**App entry points.**

| | `recover` — existing profile | `restore` — empty profile |
|---|---|---|
| Use | Forgotten passphrase or lost device factor | New computer, or an erased profile |
| Inputs | Words and new passphrase. `RR` is `identity.recovery` | Recovery file (base64, at most 256 characters, decoding to 105 bytes), words and new passphrase |
| Precondition | `RR.ik_pub` MUST equal the current record's `ik_pub`; the messaging client is locked first | No identity record exists |
| Handling of `RR` | Unchanged | Written to `identity.recovery` before recovery; deleted again if recovery fails and no identity was installed |

**What recovery restores.**

| | Existing profile | Empty profile |
|---|---|---|
| Identity key | Same | Same |
| Identity record | New generation (new passphrase, new `DKM`, new parameters) | New |
| Database | The same store opens (`db_key` is unchanged, §4.2): contacts, conversations, sessions, mailboxes and preferences remain | A new empty store: no contacts, conversations, attachments, mailbox configuration or queued messages |
| Recovery kit | Unchanged; the same words and file keep working | The imported file becomes `identity.recovery` |
| Prekeys | Retired and replaced before new Initials are accepted (below) | Same obligation |

Restoring the same identity into two profiles produces two independent profiles
that share an identity key. They do not merge or synchronize.

**Prekey hygiene (MANDATORY on every recovery path).** A recovered profile MUST
generate a fresh SPK and a new OPK pool with new ids, never re-uploading or
reactivating pre-recovery key ids, and MUST upload new bundles with fresh signed
manifests ([S06 §5.4](06-key-agreement-ratchet.md)) to all mailboxes before it
accepts inbound Initials. X3DH Initials that reference pre-recovery SPK or OPK
ids MUST fail; implementations MUST NOT special-case them into success.
Rationale: an older copy of a profile can contain one-time prekey private keys
that were consumed after the copy was made; reviving them would make captured
Initials replayable.

The identity layer hands this obligation to the messaging layer durably:

```
marker path = <profile>/prekey-recovery-<lowercase hex of ik_pub>
marker      = CSPRNG(32)        // the recovery generation, written atomically (§12.2)
```

Step 9 writes a new marker before the recovered record is installed. While the
store's completed recovery generation differs from the marker, the messaging
layer retires every stored prekey (its id joins the used-id set and its private
key is deleted), deactivates single-use handshake capabilities, publishes fresh
bundles and then records the marker value as complete. Until then it refuses to
accept inbound Initials. The marker stays after completion, so neither a restart
nor a passphrase change can erase an outstanding obligation.

### 13.3 Backup Verification

Before the user can finish saving the kit, the UI requires:

```
1. The words have been revealed and the recovery file has been downloaded.
2. indices = 3 distinct uniform random values in [0, 24)
3. For each index i: the user enters word #(i + 1);
   compare trim(lowercase(input)) with words[i].
4. All 3 must match; only then can the user acknowledge the kit.
```

This check is a usability safeguard in the UI. The native service does not
enforce it.

### 13.4 Worked Example (24 words)

Non-normative.

```
Given (recovery file, 105 bytes):
  ik_pub          = 32 bytes
  nonce_recovery  = 24 bytes
  enc_ik_recovery = 48 bytes (32 ciphertext + 16 tag)
  phrase_length   = 24

Step 1: decode
  recovery_seed = BIP39_Decode("word1 word2 ... word24")       // 32 bytes

Step 2: derive the AEAD key
  K_recovery = HKDF-SHA256(IKM = recovery_seed, salt = ik_pub,
                           info = "najwa/v1/recovery", length = 32)

Step 3: decrypt
  AAD_recovery = "najwa/v1/recovery" || ik_pub                  // 49 bytes
  IK_priv = XChaCha20-Poly1305-Decrypt(K_recovery, nonce_recovery,
                                       enc_ik_recovery, AAD_recovery)   // 32 bytes

Step 4: verify
  Ed25519_PublicKey(IK_priv) == ik_pub
```

A 12-word record works the same way with a 16-byte seed. The seed length does
not change `IK_priv`, which is always the full 32-byte key encrypted at
generation.

### 13.5 Replacing the Recovery Kit

```
1. Lock the messaging client and the identity.
2. Unlock with the current passphrase through the limiter (§10.1).
3. (words, RR) = §13.1 with phrase_length = 24
4. Write RR to identity.recovery (§12.2).
5. Hold the words for the user as in §13.0.
```

After replacement the old words do not match the file in the profile. A
complete old kit — old words with a copy of the old file — still decrypts
`IK_priv`. Replacing a kit does not revoke earlier kits.

## 17. Device Key Material (DKM) Storage

`DKM` is 32 bytes from the OS CSPRNG. It never appears in the profile directory
and never in plaintext at rest. Platform details:
[Windows TPM](../../crates/najwa-identity/WINDOWS-TPM.md),
[Linux TPM](../../crates/najwa-identity/LINUX-TPM.md),
[macOS Secure Enclave](../../crates/najwa-identity/MACOS-SECURE-ENCLAVE.md).

### 17.1 Generations

- A new `DKM` is generated for each new identity record from creation (§4.1) and
  recovery (§13.2). A passphrase change re-protects the existing `DKM` value
  under the new generation (§12.1).
- The generation id `gen` is the lowercase hex encoding of the record's `saltP`
  (64 characters).
- Credential names:

  ```
  hardware-protected : "Najwa/DKM/record/" || gen
  approved OS storage: "Najwa/DKM/record/approved-software/" || gen
  ```

- Storing a generation MUST NOT overwrite an existing credential or hardware
  key. A store that finds either fails.
- A generation is stored before the record that needs it and becomes live when
  that record commits (§12.3). Preparing a new generation never touches the
  credential of the live record.
- A hardware backend MUST unwrap what it has just wrapped, and compare the result
  with `DKM` in constant time, before it reports success. An identity is never
  published with a device factor the hardware cannot open.

### 17.2 Backend Selection

The app MUST be built with the hardware backends and the approval-gated OS
storage of §17.4; the build refuses any other configuration. The hardware
backend is the Windows TPM, the Linux TPM or the macOS Secure Enclave, according
to the OS.

**Storing a new generation:**

```
1. Store with the hardware backend (§17.3).
2. If that fails and OS-storage approval is active for this operation (§17.4):
     store in approved OS storage.
3. Otherwise FAIL with a device-factor error (app: keystore_unavailable).
```

**Retrieving a generation's DKM:**

```
1. If an approved OS-storage credential exists for gen: decode it (§17.4) and
   return its DKM. A malformed credential or binding mismatch is an error.
2. Otherwise retrieve from the hardware backend. Its failure is final.
```

There is no other source. A raw 32-byte credential, a credential that is not a
valid envelope of the backend, and any file-based key are rejected. The app
refuses to start when the environment variable `NAJWA_DKM_FILE` is set, and
hardware-enabled builds ignore it.

### 17.3 Hardware Backends

All three backends wrap the same 64-byte plaintext shape:

```
plaintext = SHA-256(label || UTF8(credential name)) || DKM      // 32 + 32 bytes
```

On unwrap, a backend MUST check that the plaintext is exactly 64 bytes and that
its first 32 bytes equal the binding for this credential name. An envelope moved
to another generation's name therefore fails.

| | Windows | Linux | macOS |
|---|---|---|---|
| Hardware key | RSA-2048 key in the Microsoft Platform Crypto Provider (TPM 2.0), current-user scope, decrypt-only, non-exportable | Keyed-hash sealed object under an RSA-2048 storage primary in the owner hierarchy; `fixedTPM`, `fixedParent` | P-256 private key generated in the Secure Enclave; permanent; non-exportable |
| Hardware key name | `Najwa.DKM.v2.` + lowercase hex of SHA-256(credential name) | none (transient TPM objects only) | Application tag `com.najwa.identity.enclave.v2.` \|\| SHA-256(credential name) |
| Binding `label` | `Najwa/v2/TPM/DKM\0` | `Najwa/v2/Linux-TPM/DKM\0` | `Najwa/v2/Secure-Enclave/DKM\0` |
| Wrapping | RSA-OAEP, SHA-256, empty label | TPM2_Create (seal) / TPM2_Unseal over an encrypted, salted session | ECIES: cofactor ECDH, X9.63 KDF with SHA-256, AES-GCM |
| Stored envelope | `NJWTPM01` \|\| 256-byte ciphertext (264 bytes) | `NJWLTP01` \|\| public_len(u16 BE) \|\| private_len(u16 BE) \|\| TPM public area \|\| TPM private blob (12–4096 bytes), hex-encoded | `NJWMSE01` \|\| ciphertext (1–4096 bytes) |
| Envelope store | Credential Manager generic credential | Secret Service item (service `com.najwa.identity`) | Generic password in the data-protection Keychain (service `com.najwa.identity`) |
| User gesture | none | none | none |

### 17.4 Approved OS Key Storage

When hardware protection is unavailable, the user may approve OS key storage.
The credential is a 72-byte blob:

| Offset | Size | Field |
|--------|------|-------|
| 0 | 8 | `NJWAPR01` |
| 8 | 32 | `SHA-256("Najwa/approved-software/v1\0" \|\| saltP \|\| ik_pub)` |
| 40 | 32 | `DKM` |

It is stored under `Najwa/DKM/record/approved-software/<gen>` in Credential
Manager (Windows), the Secret Service (Linux, service `com.najwa.identity`) or
the Keychain (macOS, service `com.najwa.identity`). On retrieval the blob MUST be
exactly 72 bytes, start with the magic and carry the binding of this record's
`saltP` and `ik_pub`.

Rules:

- OS storage MUST NOT hold a new generation unless the user explicitly approved
  it for this profile. It MUST NOT be used silently after a hardware failure.
- Approval is offered only after an identity operation failed because the device
  factor was unavailable: a `keystore_unavailable` error, or a record whose
  device factor cannot be read. The user must tick an explicit confirmation;
  the request carries `confirmed: true`. `confirmed: false` creates nothing.
  Approval is refused while the identity is unlocked.
- Approval does not replay the failed operation. The user repeats it and enters
  the passphrase again.
- The approval is held for the profile in memory and applied to each
  synchronous identity operation through a flag scoped to that operation's
  thread. It cannot leak to another thread or outlive the operation.
- Persistence: the credential is bound to one record generation (`saltP` and
  `ik_pub`). At startup, a profile whose current record uses OS storage is
  treated as approved; every other profile is not.
- Even with approval, each new generation tries hardware first (§17.2).
- Approval never makes an existing hardware generation readable. A lost hardware
  key still needs the recovery kit (§19.2).
- The app shows the state: `protection: "os-keystore"` and
  `hardware: "unavailable"` when the record uses OS storage;
  `protection: "hardware"` with `hardware: "unverified"` before unlock and
  `hardware: "protected"` after a hardware-protected unlock.

### 17.5 Failure Behavior

- Any backend failure — no TPM or Secure Enclave, a missing hardware key, a
  locked or absent keyring, a wrong envelope, a binding mismatch, a provider or
  key-policy mismatch — is a device-factor error. It never yields a usable
  substitute. (§9.1 step 4 substitutes random bytes only to keep timing uniform;
  they can never decrypt.)
- If the device factor cannot be read when the record is loaded, the attempt
  counter cannot be authenticated and the limiter starts locked out (§10.1). The
  identity cannot be unlocked until the factor is readable (the next attempt then
  reads the counter again), or until the recovery kit is used.
- A missing generation is never re-created from another source.

### 17.6 Deletion

- Deleting a generation removes the hardware key before the stored envelope. A
  hardware error is reported, not treated as success, and the envelope is then
  kept (Windows, macOS). On Linux there is no persistent TPM object; deletion
  removes the Secret Service item.
- A hardware key that provably no longer exists counts as deleted. On Windows
  these provider statuses are proof: `NTE_BAD_KEYSET` (`0x80090016`) and
  `NTE_NOT_FOUND` (`0x80090011`), no such key; `TPM_E_PCP_WRONG_PARENT`
  (`0x8029040E`) and `TPM_20_E_INTEGRITY` (`0x8028009F`), the key belongs to a
  storage parent the TPM no longer has because it was cleared. Every other
  status is a hardware error, including an absent or firmware-disabled TPM
  (`TBS_E_TPM_NOT_FOUND`) and a TPM that is not ready or not provisioned: the key
  may work again later.
- Approved OS storage is deleted by removing its credential.
- After a generation commit, the previous generation is deleted (§12.3 step 5).
- Profile erasure ([S13 §11](13-privacy-hardening.md)) deletes the current
  generation and then the profile files.
- A copy of an envelope (and, on Windows, of the provider's key file) made before
  deletion may still unwrap on the same hardware. Deletion does not revoke such
  copies.

## 18. Identity Lifecycle

| Event | Action |
|-------|--------|
| **Create** | New passphrase (§11.1) → `IK_priv`, `DKM`, calibration, record (§4.1) → store `DKM` (§17.2) → 24-word recovery record (§13.1) → generation commit (§12.3) → messaging client opens the store → UI walks the user through the recovery kit (§13.0, §13.3) |
| **Unlock** | Limiter (§10.1) → retrieve `DKM` → Argon2id → `KEK` → decrypt `IK_priv` (§9.1) → messaging client derives `db_key` and opens the store |
| **Lock** | The messaging client drains operations, zeroizes keys and closes the store; the identity manager drops the unlocked identity and reloads the record, counter and timing reference; pending recovery words are discarded. Inactivity locking defaults to 300 s, configurable from 60 to 3600 s ([S13 §8](13-privacy-hardening.md)). Cover traffic continues while locked ([S10](10-cover-traffic.md)). The app starts locked after a restart |
| **Passphrase change** | §12.1 |
| **Replace recovery kit** | §13.5 |
| **Recover / restore** | §13.2 |
| **Device-factor loss** | §19 |
| **Erase profile** | [S13 §11](13-privacy-hardening.md): persist the erasure marker, delete the current device-factor generation (§17.6), erase the profile files |
| **Own identity rotation** | Not provided: the app never replaces its own identity key |

### 18.1 Contact Identity Rotation

A peer may announce that its identity key changed. The receive path accepts the
announcement as control subtype `0x21` (`IdentityRotation`) inside an encrypted
message ([S07 §2.1](07-message-format.md),
[Message Types](../reference/message-types.md)). The body is exactly 200 bytes:

| Offset | Size | Field |
|--------|------|-------|
| 0 | 32 | `old_ik_pub` |
| 32 | 32 | `new_ik_pub` |
| 64 | 8 | `timestamp` (Unix seconds, u64 BE) |
| 72 | 64 | `sig_old = Ed25519_Sign(old IK_priv, body[0:72])` |
| 136 | 64 | `sig_new = Ed25519_Sign(new IK_priv, body[0:72])` |

The receiver MUST reject the announcement unless all of the following hold:

1. The body is exactly 200 bytes.
2. `old_ik_pub` equals the contact's pinned identity key.
3. `old_ik_pub` and `new_ik_pub` are valid Ed25519 public keys.
4. `sig_old` verifies under `old_ik_pub` over `body[0:72]`.
5. `sig_new` verifies under `new_ik_pub` over `body[0:72]`.

On acceptance, in the same transaction as the rest of the message, the receiver
replaces the pinned key (only if it still equals `old_ik_pub`) and records an
identity-history row `(contact, old_ik_pub, new_ik_pub, rotated_at = now,
reason = "rotation")` ([S03 §5.14](03-encrypted-storage.md)). `timestamp` is
signed but not checked.

Subtype `0x26` (`RotationAnnouncementRequest`) MUST have an empty body; the
receive path accepts it and takes no action.

The app does not send `0x21` or `0x26`.

A different identity key arriving through a new invitation is not covered by
this procedure. It is not proof of continuity; see
[S05 §8](05-contact-establishment.md).

## 19. Device-Factor Loss and Hardware Record Mode

### 19.1 Detection

The device factor is lost when retrieval of the record's generation fails
(§17.5): the TPM was cleared or replaced, the hardware key was deleted, the
profile was copied to another computer, or the envelope is missing from the
credential store. The identity record stays unchanged. The app reports the failure
and offers OS-storage approval (§17.4) and recovery.

### 19.2 Recovery from Hardware Loss

1. The user restores access with the recovery kit (§13.2, `recover`).
2. Recovery generates a new `DKM` and stores it with the hardware backend; if
   that fails and the user approved OS storage, in OS storage (§17.2).
3. The identity, the database and the contacts remain (§13.2).

Without the recovery kit, an identity whose device factor is lost cannot be
opened. Approval of OS storage cannot bypass a missing hardware key.

### 19.3 Mode Migration

Record mode `0x02` (a hardware-wrapped record layout) is reserved. An
implementation MUST NOT write a record with mode `0x02`. The migration API
fails closed:

```
migrate_to_hardware(record, passphrase, hw_wrap)     → Err(HardwareError)
migrate_to_standard(hw_record, passphrase, hw_unwrap) → Err(HardwareError)
```

Both calls MUST return `HardwareError` ("hardware-mode migration is unavailable
in this build") without reading a device factor, running Argon2id or invoking
the supplied callback. Hardware protection is provided only through the device
factor of the standard record (§17).

## 20. Security Properties

| Threat | Hardware backend (TPM, Secure Enclave) | Approved OS storage |
|--------|----------------------------------------|---------------------|
| Network attacker | Protected | Protected |
| Copy of the profile directory (backup, disk image) | Protected: `DKM` is sealed to this computer's hardware | Protected unless the attacker also obtains the OS credential store and the user's OS login secret |
| Stolen computer, app locked | `DKM` is usable only by code running as this OS user on this computer; without that, no passphrase guess can be tested | Anyone who can unlock the OS account or its credential store can read `DKM` and guess offline at Argon2id cost |
| Malware running as the same OS user, app locked | Can ask the hardware to unwrap `DKM` (no PIN or user gesture), then guess the passphrase offline at Argon2id cost | Can read `DKM`, then guess offline at Argon2id cost |
| Compromised OS or app while unlocked | Not protected | Not protected |
| Holder of a complete recovery kit | Obtains `IK_priv` | Obtains `IK_priv` |

Protection against a compromised OS at run time would need signing inside the
hardware. This specification does not provide it.

### 20.1 Limitations

- **The attempt limiter binds only the app's unlock path.** Code running as the
  same OS user can obtain `DKM` and guess offline. It can also put back an older
  valid counter file: the tag authenticates the content, not its freshness.
- **The lockout window follows the system clock.** Whoever controls the clock
  can shorten the 24-hour lockout. Each guess still costs a full Argon2id run.
- **A missing or damaged counter file locks the identity** until it is
  authentic again or the recovery kit is used (§10.1).
- **A complete recovery kit grants the identity** without the passphrase or the
  device. Replacing a kit does not revoke older kits (§13.5). The profile keeps
  its own copy of the recovery file, so on this computer the words are the only
  secret part.
- **Recovery restores the identity, not history.** An empty profile gets no
  contacts, conversations or attachments back (§13.2).
- **OS key storage is protected by the OS account**, not by hardware.
- **The hardware backends have no user-presence gate:** no TPM PIN, Touch ID or
  confirmation dialog.
- **Linux cannot attest physical hardware:** `/dev/tpmrm0` may be a virtual TPM
  whose protection depends on the hypervisor.
- **Deletion does not revoke earlier copies** of an envelope on the same
  hardware (§17.6).
- **Decrypted data is exposed while unlocked:** a compromised unlocked process
  can read the identity key, the database key and plaintext.

## 21. Conformance Checklist

- Ed25519 identity key from a 32-byte CSPRNG seed; `IK_priv` persisted only encrypted (§2).
- Per-mailbox signing key derivation and `MailboxCertificate` signing (§2.2).
- Database key derivation with salt `najwa-sqlcipher-key` and info `najwa/v1/sqlcipher-key` (§4.2).
- Record creation with `DKM` as HKDF salt and `najwa/v1/kek` (§4.1).
- Argon2id bounds, 512 MiB target halving to the 64 MiB floor, core-count parallelism, ≥ 1000 ms calibration capped at 100 iterations (§6).
- 192-byte record serialization and validation: magic, version ≤ `0x03`, reserved zero, checksum (§7.1, §7.3).
- `AAD_identity` (85 bytes) and `AAD_recovery` (49 bytes) exactly as in §8.
- Unlock with no early return, Argon2id always run, single generic error, floor of `T_ref × 1.1 + 200 ms` plus 0–50 ms jitter (§9.1).
- `T_ref` persisted per generation, authenticated with `DKM`, seeded at 1000 ms (§9.1).
- Durable attempt counter: reloaded at each attempt, counted before the passphrase test, HMAC-tagged with `DKM`, fail-closed on missing or invalid state, backoff `1000 ms × 2^(N−1)`, lockout at 10, 24-hour expiry (§10).
- Passphrase length (12 characters to 1024 bytes), confirmation and NFC normalization (§11).
- New passphrases only: zxcvbn estimate ≥ 2^40 guesses with and without whitespace, else `weak_passphrase` (§11.1).
- Length and strength enforced in the identity core at every new-passphrase entry point, before any state changes; never at unlock (§11.1).
- Passphrase change through the limiter with a new salt, nonce and generation (§12.1).
- Durable atomic write with a random temporary name and `fsync`, then rename and directory `fsync` (POSIX) or `MoveFileExW` with write-through (Windows) (§12.2).
- Generation commit with rollback of the new generation and the recovery file; the previous generation is deleted only after the durable write succeeds, and both are kept when the write fails after the replace (§12.3).
- Recovery kit: independent seed, HKDF with `ik_pub` salt, AEAD-sealed `IK_priv`, 105-byte record, 24 words in the app (§13.0, §13.1).
- Recovery: phrase-length check, AEAD and public-key verification, new record and `DKM`, fingerprint match for an existing profile (§13.2).
- Prekey-recovery marker written before install; Initials refused until fresh prekeys are published (§13.2).
- Kit replacement only after passphrase authentication (§13.5).
- Device-factor generations named by `saltP`, never overwritten, unwrap-verified before use (§17.1).
- Hardware backends on Windows, Linux and macOS with name-bound 64-byte plaintext; no raw, file or unscoped fallback (§17.2, §17.3).
- OS storage only after explicit, identity-bound, persistent approval; hardware tried first (§17.4).
- Generation deletion removes the hardware key before the envelope; only a provably absent key counts as deleted (§17.6).
- Rotation announcements (`0x21`) verified against the pinned key with both signatures; `0x26` accepted with an empty body (§18.1).
- Mode `0x02` never written; migration API fails closed without touching key material (§19.3).
- Secrets zeroized per [S01 §6.1](01-crypto-primitives.md).
